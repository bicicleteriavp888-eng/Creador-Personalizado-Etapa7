PROMPT MAESTRO — EVOLUCIÓN DE CREADOR-KIOSK 2.1

Proyecto TallerArg — Constructor profesional de distribuciones Linux

1. OBJETIVO GENERAL

Actúa como arquitecto de software, desarrollador Linux senior,
especialista en Python, interfaces gráficas, Fedora, Kickstart, creación
de imágenes ISO, seguridad y automatización.

Tu misión es analizar, corregir, reorganizar y ampliar el proyecto
existente Creador-kiosk, transformándolo en una herramienta profesional
para construir, configurar, personalizar, compilar y validar
distribuciones Linux.

IMPORTANTE: - No comenzar desde cero. - No eliminar funcionalidades
existentes sin justificación. - No reemplazar módulos funcionales por
implementaciones incompletas. - No inventar resultados de compilación o
validación. - Conservar la compatibilidad con las funcionalidades
actuales. - Realizar modificaciones sobre el código fuente real. -
Documentar cada modificación. - Mantener copias de seguridad antes de
cambios importantes.

El objetivo es desarrollar Creador-kiosk 2.0 dentro del ecosistema
TallerArg.

2. IDENTIDAD DEL PROYECTO

Nombre: Creador-kiosk 2.0. Identidad visual: TallerArg. Objetivo:
constructor de distribuciones Linux personalizadas. Distribución de
referencia: TallerArgOS Kioscoy.

La aplicación debe permitir generar diferentes perfiles de sistemas
Linux, no exclusivamente TallerArgOS Kioscoy.

Debe contemplar dos modalidades:

Modo Simple - Configuración guiada. - Opciones esenciales. - Perfiles
predefinidos. - Compilación simplificada. - Validaciones automáticas.

Modo Avanzado - Configuración detallada. - Parámetros técnicos. -
Administración de repositorios. - Personalización de Kickstart. -
Selección de paquetes. - Configuración de arranque. - Diagnóstico y
registros.

3. INTERFAZ GRÁFICA PROFESIONAL

Desarrollar una interfaz moderna inspirada en los principios visuales de
Windows 11, pero con identidad propia de TallerArg. No copiar logotipos
ni elementos de marca registrados.

Características: - Diseño moderno. - Navegación lateral. - Panel
principal. - Tarjetas informativas. - Iconografía consistente. - Tema
claro y oscuro. - Diseño adaptable a diferentes resoluciones. -
Indicadores de estado. - Mensajes de error comprensibles. - Ventanas de
confirmación para operaciones críticas.

3.1 Asistente de creación paso a paso

Implementar un asistente dividido en seis etapas: 1. Identidad del
sistema. 2. Apariencia y personalización. 3. Selección de software. 4.
Configuración del instalador. 5. Seguridad y servicios. 6. Compilación y
validación.

Cada etapa debe permitir: - Guardar cambios. - Volver a etapas
anteriores. - Validar los datos ingresados. - Mostrar errores. -
Recuperar configuraciones. - Consultar ayuda contextual.

No permitir avanzar cuando existan errores críticos de configuración.

3.2 Panel principal

Mostrar: - Última compilación. - Estado de la ISO. - Ruta del archivo
generado. - Tamaño de la ISO. - Fecha de compilación. - Hash SHA-256. -
Espacio disponible. - Dependencias instaladas. - Estado de servicios. -
Configuración activa. - Tareas pendientes. - Últimos errores.

Los indicadores deben reflejar información real obtenida del sistema.

4. COMPILACIÓN VISUAL

Desarrollar un sistema de compilación que no bloquee la interfaz
gráfica.

Incorporar: - Barra de progreso. - Etapa actual. - Tiempo
transcurrido. - Registro de ejecución. - Botón para cancelar. - Estado
de cada operación. - Mensajes de éxito o error. - Recuperación ante
interrupciones.

Etapas sugeridas: 1. Diagnóstico del entorno. 2. Comprobación de
dependencias. 3. Validación de configuración. 4. Preparación de
repositorios. 5. Preparación del entorno de compilación. 6. Construcción
de la imagen. 7. Verificación del resultado. 8. Generación de hashes. 9.
Elaboración del informe.

El porcentaje de progreso debe basarse en información real de las
operaciones cuando esté disponible. No simular porcentajes de avance.

La cancelación debe ser controlada, sin dejar procesos huérfanos,
archivos inconsistentes o montajes temporales abandonados.

5. SISTEMA DE PERFILES

Implementar perfiles reutilizables.

Perfiles iniciales: - Kiosco navegador. - Kiosco multiventana. - Equipo
de oficina. - Terminal de atención. - Estación de trabajo.

Funciones: - Crear perfiles. - Editar perfiles. - Duplicar perfiles. -
Eliminar perfiles con confirmación. - Guardar configuraciones. -
Importar perfiles. - Exportar perfiles. - Validar perfiles. - Recuperar
configuraciones anteriores.

Los perfiles deben utilizar un formato estructurado, preferentemente
JSON o YAML. Incluir control de versiones del formato y validación de
datos.

6. CATÁLOGO DE APLICACIONES

Implementar un catálogo organizado por categorías: - Navegadores. -
Multimedia. - Ofimática. - Utilidades. - Herramientas administrativas. -
Seguridad. - Desarrollo. - Accesibilidad.

No asumir que un paquete existe sin comprobarlo en los repositorios

Permitir seleccionar y deseleccionar aplicaciones. Validar dependencias
y conflictos antes de iniciar la compilación.

7. DIAGNÓSTICO PREVIO

Debe comprobar: - Distribución Linux anfitriona. - Versión del
sistema. - Arquitectura. - Memoria disponible. - Espacio en disco. -
Dependencias. - Herramientas de compilación. - Docker o entorno de

Repositorios. - Permisos. - Estado de SELinux. - Herramientas de
creación ISO. - Disponibilidad de QEMU.

Clasificar resultados: - Correcto. - Advertencia. - Error. - No
disponible.

No comenzar una compilación cuando exista un error crítico. Generar un
informe de diagnóstico.

8. MOTOR KICKSTART

Separar la administración de Kickstart del constructor principal.

Crear un módulo especializado que permita: - Crear archivos Kickstart. -
Editar configuraciones. - Validar sintaxis. - Comprobar paquetes. -
Verificar particiones. - Revisar cargador de arranque. - Configurar
usuarios. - Configurar red. - Configurar seguridad. - Configurar
servicios. - Administrar scripts de instalación.

Contemplar las diferencias entre Legacy BIOS y UEFI. No generar
configuraciones incompatibles entre sí.

Validar especialmente: - bootloader. - particiones BIOS. - particiones
EFI. - /boot. - partición raíz. - sistemas de archivos. - tablas de
particiones. - opciones de instalación.

Nunca eliminar automáticamente particiones o datos del usuario sin una

9. SEGURIDAD Y CONFIABILIDAD

Incorporar un módulo específico de seguridad.

Requisitos: 1. Verificación de firmas de paquetes. 2. Comprobación de
procedencia de RPM. 3. Lista de paquetes permitidos y bloqueados. 4.
Validación de repositorios. 5. Comprobación de versiones. 6. SELinux en
modo enforcing cuando corresponda. 7. Firewall habilitado. 8. SSH
opcional y protegido. 9. Validación de espacio disponible. 10. Registro
de operaciones privilegiadas. 11. Protección ante interrupciones. 12.
Verificación de integridad de resultados.

Separar la interfaz gráfica de las operaciones administrativas. No
ejecutar toda la aplicación como root. Utilizar mecanismos controlados
de elevación de privilegios.

No utilizar comandos construidos mediante concatenación insegura de
cadenas. Preferir subprocess con argumentos separados. Validar rutas,
parámetros y entradas externas.

10. LABORATORIO DE ISO

Esta funcionalidad es prioritaria.

Crear una pestaña independiente llamada LABORATORIO.

Su objetivo es comprobar si una ISO realmente funciona.

La aplicación debe diferenciar tres estados independientes: 1. GENERADA.
2. VALIDADA. 3. PROBADA.

No considerar una ISO probada simplemente porque pasó las verificaciones
estáticas.

10.1 Verificación básica

-   Comprobar existencia.
-   Comprobar tamaño.
-   Calcular SHA-256.
-   Verificar integridad.
-   Comprobar permisos.
-   Detectar archivos faltantes.

10.2 Verificación estructural

-   Analizar ISO9660.
-   Detectar estructura de arranque.
-   Comprobar compatibilidad BIOS.
-   Comprobar compatibilidad UEFI.
-   Detectar archivos EFI.
-   Detectar kernel.
-   Detectar initramfs.
-   Comprobar cargadores de arranque.
-   Revisar tablas de particiones híbridas cuando corresponda.

Utilizar herramientas como xorriso, isoinfo, file y otras disponibles en
el sistema.

No considerar suficiente la presencia de archivos EFI para afirmar que
UEFI funciona.

10.3 Verificación Kickstart

-   Comprobar sintaxis.
-   Detectar directivas incompatibles.
-   Comprobar particiones.
-   Verificar paquetes.
-   Comprobar scripts.
-   Detectar configuraciones inseguras.
-   Verificar consistencia general.

10.4 Verificación de paquetes y repositorios

-   Detectar paquetes ausentes.
-   Comprobar dependencias.
-   Verificar versiones.
-   Detectar conflictos.
-   Revisar repositorios.
-   Comprobar procedencia.

10.5 Pruebas virtuales

Integrar QEMU/KVM cuando esté disponible.

Permitir: - Arranque Legacy BIOS. - Arranque UEFI. - Prueba de menú de
inicio. - Detección del instalador. - Prueba de instalación en disco
virtual. - Registro de resultados.

Las pruebas deben ejecutarse sobre discos virtuales aislados. No
utilizar discos físicos del usuario para pruebas automáticas.

Si una prueba no puede realizarse, mostrarla como pendiente o no
disponible, nunca como aprobada.

10.6 Informe de laboratorio

Generar un informe que incluya: - Nombre de ISO. - Versión. - Fecha. -
Tamaño. - SHA-256. - Arquitectura. - Compatibilidad BIOS. -
Compatibilidad UEFI. - Resultado Kickstart. - Resultado de paquetes. -
Resultado de pruebas virtuales. - Errores. - Advertencias. -
Herramientas utilizadas.

Permitir exportar el informe a TXT y HTML; PDF como funcionalidad
adicional.

21. SISTEMA OBLIGATORIO DE SEGUIMIENTO (NUEVO EN 2.1)

El archivo `documentation/SEGUIMIENTO_ETAPAS_2.1.md` es el registro vivo
del avance. Debe actualizarse al comenzar y cerrar cada sesión de trabajo.
No confiar en memoria de conversación ni en estados declarados sin evidencia.

Estados permitidos:
- PENDIENTE: no hay implementación verificable.
- EN CURSO: existe trabajo iniciado, pero no cumple todos los criterios.
- BLOQUEADA: falta una dependencia, permiso, equipo o decisión; explicar cuál.
- IMPLEMENTADA: el código existe, pero todavía no superó todas las pruebas.
- VALIDADA: criterios de aceptación superados con pruebas ejecutadas y evidencia.

Una etapa solo puede marcarse VALIDADA si se registra: fecha, commit o
identificador del cambio (si existe), archivos afectados, comandos ejecutados,
resultado exacto de pruebas, evidencia generada y limitaciones conocidas.
No convertir IMPLEMENTADA en VALIDADA por inspección visual ni por presencia
de archivos. No inventar resultados ni reutilizar resultados de otra máquina.

Al iniciar cada sesión:
1. Leer este Prompt Maestro, el seguimiento y la auditoría más reciente.
2. Comprobar el estado real del repositorio y detectar cambios desde el último
   registro.
3. Identificar la etapa activa y sus bloqueos.
4. Crear una copia de seguridad antes de cambios estructurales o destructivos.
5. Elegir una unidad de trabajo pequeña y verificable.

Al terminar cada unidad de trabajo:
1. Ejecutar `python3 -m compileall -q .`.
2. Ejecutar las pruebas específicas y luego `python3 -m pytest -q`.
3. Ejecutar prueba de humo de GUI cuando el cambio afecte la interfaz.
4. Registrar comandos y resultados exactos; si una dependencia falta, indicar
   que la prueba no pudo ejecutarse, no que pasó.
5. Actualizar `documentation/SEGUIMIENTO_ETAPAS_2.1.md`, la auditoría y
   `CHANGELOG.md` cuando corresponda.
6. No comenzar una etapa dependiente si la puerta de la etapa anterior falla.

El seguimiento debe incluir para cada etapa: objetivo, subtareas, estado,
criterios de aceptación, evidencia, bloqueos, archivos modificados y próximo
paso concreto. Mantener además un registro cronológico de sesiones.
